# 🪟 Aetox v1.10.26

วันที่ 29 ตุลาคม 2026

**ผังองค์กรที่มีแต่แผนกสร้างได้แล้ว เดิมถูกปฏิเสธว่า «ไม่ได้สร้างอะไร» ทั้งที่เขียนแผนกได้อยู่ · ภาพของจุดเดียว — แถวหนึ่งวางตรงไหน ปุ่มหนึ่งหน้าตาเป็นอย่างไร — ถูกวาดในคำตอบก่อนจะกลายเป็นหน้า proposal และหน้าตัดสินเฉพาะส่วนที่เปลี่ยน ไม่ประกอบจอใหม่ทั้งจอเพื่อดูแถวเดียว**

## องค์กร: ผังที่มีแต่แผนก

- **เดิมสั่งตั้งแผนกใหม่บนทีมเดิมไม่ได้เลย** ผู้ใช้สั่งให้ตั้งแผนกคอนเทนต์และการตลาดโดยใช้หัวหน้า `chief` ที่มีอยู่กับทีมเดิมสามทีม และคงสมาชิกเดิมไว้ ส่งผังสองครั้งสองแบบแล้วถูกปฏิเสธทั้งคู่ แบบแรกได้ «the plan makes nothing» เพราะ `check()` นับแค่ `new_agents` กับ `teams` ว่าเป็นการสร้าง ทั้งที่ `applyOrgDraft` เขียนแผนกได้อยู่แล้ว แบบที่สองคือเอารายละเอียดทีมเดิมไปใส่ใน `teams` จึงชนชื่อซ้ำ ซึ่งถูกตามกติกา แต่ข้อความไม่ได้บอกว่าทีมเดิมควรอยู่ตรงไหน
- **แผนกและบริษัทนับเป็นการสร้าง** ผังที่มีแต่แผนกจึงผ่านการตรวจและการ์ดขึ้นให้ยืนยัน กดสร้างแล้วเกิดเฉพาะแผนก ทีมเดิมไม่ถูกเขียนทับ และ undo ไม่พาทีมเดิมไปด้วย
- **เอเจนใหม่ที่ไม่มีที่นั่งถูกจับเมื่อผังสร้างหน่วยเหนือเอเจน** ไม่ใช่เฉพาะเมื่อผังมี `teams` เอเจนที่ลอยอยู่จึงไม่ผ่านไปถึงขั้นเขียน
- **ปฏิเสธทีมซ้ำแยกเป็นสองกรณี** ชื่อมีอยู่แล้วบอกให้ไประบุใน `departments.teams` (แผนกก่อตัวเองบนทีมที่มีหัวหน้าอยู่แล้ว ไม่ได้เขียนทีมนั้นซ้ำ) และชื่อซ้ำภายในผังเดียวกันบอกให้เปลี่ยนชื่อ เดิมสองเรื่องนี้ใช้ข้อความเดียว คนสั่งจึงแก้ไม่ถูก
- **`orgDraftShape` บอกกติกานี้ล่วงหน้า** ว่า `teams` ของแผนกรับทีมเดิมที่มีหัวหน้าได้ และห้ามเขียนทีมเดิมซ้ำ โมเดลจึงไม่ต้องลองผิดสองรอบให้เสียเวลา
- **ข้อความผลลัพธ์ไม่พิมพ์ «0 new agent(s)»** ในผังที่ใช้ของเดิม เพราะศูนย์เอเจนใหม่คือผังที่ถูก ไม่ใช่ผังที่ล้มเหลว
- **อ้างทีมที่ไม่มีถูกปฏิเสธโดยไม่เขียนแผนก** และทีมหายระหว่างดราฟต์กับกดสร้างทำให้ `Create` ปฏิเสธโดยไม่เหลือแผนกครึ่งทาง

## คำตอบ: ภาพของจุดเดียวก่อนหน้า proposal

- **เดิมทุกครั้งที่ต้องตัดสินหน้าตา ออกมาเป็นหน้า options ทั้งหน้า** สิ่งที่ต้องตัดสินมักเป็นจุดเดียว — แถวหนึ่งวางตรงไหน ปุ่มหนึ่งหน้าตาเป็นอย่างไร รูปแบบไหนอ่านง่ายกว่า — แต่คำตอบพาไปหน้า HTML ที่ต้องประกอบจอใหม่ทั้งจอ คัดลอกสไตล์ทั้งชุด และกินบริบทมากกว่าที่การตัดสินนั้นต้องการ
- **ประตู visuals สั่งให้วาดจุดเดียวก่อน** พื้นผิวที่แสดงภาพมี SVG กับ panel อยู่แล้ว ตัวอย่างหนึ่งจุดจึงไม่ต้องติดตั้งอะไร และผู้ใช้เห็นในคำตอบที่กำลังอ่านอยู่ สกิล `aetox-answer-visuals` ได้หัวข้อใหม่ «Before a page, a picture»: จุดที่ชี้ได้ไม่ใช่เรื่องของหน้า options หน้า options ไว้สำหรับหน้าตาที่ต้องสลับดูทั้งสถานะ
- **หน้าตัดสินเฉพาะส่วนที่เปลี่ยน** สกิล `aetox-proposal-page` ได้หัวข้อ «The part, not the screen»: ค้นหาสิ่งแวดล้อมไม่กี่ครั้งแล้วเขียนหน้า คัดลอก markup ของส่วนที่เปลี่ยนจากคอมโพเนนต์แล้วหยุด ถ้าหาองค์ประกอบรอบข้างไม่เจอในสองครั้ง ให้วาดด้วยคลาสของแอปแบบย่อ พร้อมบรรทัดใต้หน้าบอกว่าเลียนแบบอะไรไว้ ห้ามสร้างจอใหม่ทั้งจอเพื่อตัดสินแถวเดียว และเมื่อสิ่งที่เสนอไม่มีที่อยู่เดิม «before» คือที่ว่างนั้น ไม่ต้องจำลอง markup อะไรเลย
- **สไตล์ที่คัดลอกมาต้องเข้าตามลำดับที่แอปโหลด** `styles/palette.css` (สีดิบ) → `styles/theme.css` (token เชิงความหมาย) → `styles/type.css` → `style.css` แล้วตามด้วยบล็อก `<style>` ของคอมโพเนนต์เอง token ที่ไม่มีสีดิบจะแปลงเป็นอะไรก็ไม่ได้ หน้าเงียบ ๆ เสียพื้นและเส้นขอบทั้งหน้าโดยไม่มี error จึงต้องเช็กสีพื้นจริงหนึ่งจุดก่อนตัดสินส่วนที่เหลือ
- **พาธ artifact รู้ได้หลังเขียนครั้งแรก** เขียนโครงก่อน แล้วคัดลอกสไตล์กับไฟล์ประกอบลงข้าง ๆ ในสคริปต์เดียว เปิดครั้งแรกจึงไม่ใช่หน้า 404 ทั้งหน้า
- **ดูสองสถานะพอ** ของเดิมกับตัวเลือกที่เลือก ภาพหน้าจอทุกใบจ่ายด้วยบริบท ไม่ได้จ่ายด้วยหน้า
