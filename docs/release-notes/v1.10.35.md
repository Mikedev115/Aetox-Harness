# 🪟 Aetox v1.10.35

วันที่ 31 ตุลาคม 2026

**หน้าต่างที่หน้าเว็บเปิดเพื่อล็อกอินออกไปเบราว์เซอร์จริงแล้ว ไม่กลายเป็นแท็บตายที่ค้างอยู่ขั้นเดิมกี่ครั้งก็ตาม · แท็บที่ถูกวางทับที่เดิมขอผิวใหม่ทุกครั้ง แทนที่จะได้เฟรมเก่ากลับมา**

## เบราว์เซอร์: หน้าต่างล็อกอินไม่อยู่ในแท็บอีกแล้ว

- **สาเหตุ** Aetox ตอบคำขอ "เปิดหน้าต่างใหม่" ของหน้าเว็บด้วยการวาดเป็นแท็บในแอป และบอกเอนจินว่ารับเรื่องนี้แล้วโดยไม่เคยส่งหน้าต่างให้สักบาน `window.open()` จึงคืนค่า null และแท็บใหม่ไม่มี `window.opener` แต่หน้าจอล็อกอินและ OAuth สร้างขึ้นบนคู่นี้พอดี: เขียน code กลับไปที่ opener แล้วปิดตัวเอง ในแท็บทั้งสองอย่างเกิดขึ้นไม่ได้ หน้าจึงค้างอยู่ที่ขั้นที่ไม่มีวันจบ และคนที่กดซ้ำก็ได้แท็บตายเพิ่มอีกใบ (เจ้าของ 31 ต.ค. 2026: "ทำไมเวลาล้อคอินมันชอบเด้งแท็บใหม่หรือจอดำแล้วค้าง")
- **ตอนนี้** คำขอเปิดหน้าต่างที่ปลายทางเป็นการล็อกอินถูกส่งออกไปเบราว์เซอร์ของเครื่อง ผ่าน `openInBrowser` ตัวเดียวกับที่ปุ่มของหน้า «บริษัท» ใช้ ไม่ใช่ทางออกที่สอง การล็อกอินจึงจบได้ตามเงื่อนไขของผู้ให้บริการเอง
- **รู้จักสองแบบ** โฮสต์ที่เคยเจอ (`accounts.google.com`, `login.microsoftonline.com`, `login.live.com`, `appleid.apple.com`, `auth.atlassian.com`) เป็นการล็อกอินทุก path และเส้นทาง authorize (`/oauth/authorize`, `/oauth2/authorize`, `/login/oauth/authorize`, `/dialog/oauth`) ไม่ว่าโฮสต์ไหน — GitLab ที่ติดตั้งเอง เทนแนนต์ของ Auth0 และ Keycloak ของลูกค้าใช้เส้นทางเดียวกัน ซึ่งรายการโฮสต์อย่างเดียวตามไม่ทัน
- **ที่เหลือยังเป็นแท็บเหมือนเดิม** `target="_blank"` ทั่วไปไม่ได้เปลี่ยน เปลี่ยนเฉพาะหน้าต่างที่เป็นการล็อกอิน
- **ขอบเขตที่ต้องรู้ตรง ๆ** การส่งออกไปแบบนี้ไม่ได้ลงชื่อให้แท็บในแอป: แซสชันที่ผู้ให้บริการให้มาเป็นคุกกี้ของเบราว์เซอร์นั้น แท็บยังถือของตัวเอง หน้าที่เปิดชมใน Aetox จึงยังต้องลงชื่อด้วยการ redirect ตามเดิม การทำให้ป๊อปอัปทำงานในที่ได้ต้องมีหน้าต่างจริงที่มี opener ซึ่งแอปยังไม่ได้สร้าง
- **ถ้าส่งออกไม่ได้** เขียนไว้ใน log (`a sign-in window (…) could not reach the system browser`) แทนการวาดแท็บขึ้นมาแทน เพราะแท็บนั้นจะค้างแบบเดียวกับที่การแก้นี้มีอยู่เพื่อหยุด

## เบราว์เซอร์: ผิวของแท็บถูกขอใหม่ทุกครั้งที่วาง

- **สาเหตุ** การวางแท็บกลับไปที่สี่เหลี่ยมเดิมเคยเป็นการยกหน้าต่างขึ้นเฉย ๆ (`SWP_NOMOVE|SWP_NOSIZE` = เปลี่ยนลำดับ Z) ไม่มี `WM_SIZE` ไม่มี `WM_PAINT` และไม่มีอะไรไปขอเฟรมจากเอนจิน ผิวที่ถืออยู่แล้วจึงกลับมาเหมือนเดิมทุกเม็ด — ภาพที่วาดค้างตามออฟเซ็ตที่บานนั้นไม่ใช้แล้ว หรือผิวที่ยังดำตรงที่สี่เหลี่ยมเก่าสิ้นสุดลง
- **ทำไมจึงสำคัญ** การวางแท็บเกิดทุกครั้งหลังนำทาง ทุกครั้งที่สลับแท็บ และทุกครั้งที่สลับเซสชัน จึงเป็นสิ่งที่โค้ดส่วนนี้ทำบ่อยที่สุด
- **ตอนนี้** เพิ่ม `repaint()` (RedrawWindow แบบ invalidate ลูกทุกตัว + `RDW_UPDATENOW`) เรียกทุกครั้งที่วางแท็บ ทั้ง rect เดิมและ rect ใหม่ และตอนโชว์แท็บ เฟรมจึงมาถึงก่อนฟังก์ชันคืนค่า สิ่งที่เห็นหลังสลับแท็บคือผิวของรอบวางนี้ ไม่ใช่ของรอบก่อน ไม่ใส่ `RDW_ERASE` เพราะพื้นหลังที่ถูกลบคือแฟลชขาวทับหน้าที่กำลังจะวาดตัวเองอยู่แล้ว (ที่มา: WebView2Feedback #1077, #2983 — ตระกูลเดียวกับ `showPlan`)
- **เป็นการบรรเทา ไม่ใช่คำยืนยัน** อาการจอดำที่เจ้าของเจอยังไม่ได้วัดซ้ำกับรุ่นนี้ ว่าหายไปหรือไม่ การเปลี่ยนนี้ทำให้ผิวถูกขอใหม่ในจุดที่มันไม่เคยถูกขอ ซึ่งเป็นเงื่อนไขของอาการ ไม่ใช่หลักฐานว่าอาการหมดแล้ว
