# 🪟 Aetox v1.11.37

วันที่ 24 พฤศจิกายน 2026

รุ่นนี้เป็นรุ่นของชั้นวางสกิล ไม่ได้แตะหน้าจอ: ได้สกิลใหม่หนึ่งตัวที่ตอบว่า «จะรู้ได้อย่างไรว่าการเปลี่ยนแปลงนี้เสร็จพอ» และเอกสารอ้างอิงหนึ่งเรื่องที่ตอบว่า «ปุ่ม เมนู และกลุ่มควรอยู่ตรงไหน» ใต้สกิลออกแบบหน้าจอ ทั้งคู่เขียนเป็นกฎที่พาเหตุมาด้วย มีที่มาและสัญญาอนุญาตกำกับ และมีเทสต์ล็อกเนื้อหาไว้ไม่ให้เลื่อนหายระหว่างคอมมิตอื่น

## สกิลใหม่: `aetox-edge-cases`

- **เดิม** ชั้นวางมีสกิลที่บอก «ทำอย่างไร» — ออกแบบหน้าจอ เขียนโค้ด เขียนเทสต์ ตรวจความปลอดภัย — แต่ไม่มีตัวที่บอกว่าเคสไหนต้องพิสูจน์ก่อนพูดว่าเสร็จ เอเจนจึงตอบด้วยชุดเดิมทุกครั้ง คือ ว่าง, null, ใหญ่มาก ซึ่งไม่เกี่ยวกับโค้ดที่เพิ่งแก้และไม่ผูกกับอะไรที่ผู้ใช้จะเจอ
- **ตอนนี้** สกิลใหม่ `internal/skill/skills/aetox-edge-cases/SKILL.md` (102 บรรทัด) หาเคสจากสี่ที่: **สัญญา** ที่โค้ดต้องรักษา (คอมเมนต์ ชนิดข้อมูล อินเวอร์เรียนต์ สาขาความผิดพลาด ผู้เรียก) · **การตัดสินใจทุกจุดในดิฟ** (branch, การเปรียบเทียบ, index, ขอบลูป, retry, lock, กฎลำดับ, ค่าตั้งต้น) · **ฮิวริสติกที่ทำให้ระบบพัง** · **ผลลัพธ์ที่แย่ที่สุดในคำพูดของผู้ใช้** แล้วเดินย้อนกลับมาหาอินพุต ลำดับ และเวลาที่ไปถึงมัน
- เกณฑ์ที่ใช้ตัดสินว่าเคสหนึ่งนับ: อินพุต + การรัน + ผลลัพธ์ — ยังไม่รันก็เป็นได้แค่เดาที่มีชื่อ · สัญญาที่ไม่ตัดสินเรื่องหนึ่ง ๆ เป็นคำถามถึงเจ้าของ ไม่ใช่เทสต์ เพราะเทสต์จะเปลี่ยนการเดาให้กลายเป็นข้อกำหนด
- เคสจะได้รันเมื่อความล้มเหลวตกถึงคน: ข้อมูลที่เขียน ลบ หรือหาย · เงิน · ขอบเขตความเชื่อถือหรือสิทธิ์ · สิ่งที่เผยแพร่หรือส่งออกไป · จอที่คนกำลังรออยู่ เคสที่ไม่มีใครเห็นความล้มเหลวถูกเขียนชื่อแล้วตัดออกพร้อมเหตุผล และการสลับสิบแบบของผลลัพธ์เดียวก็นับเป็นเคสเดียว
- ที่ยากคือ input space (parser, codec, state machine, กฎ retry หรือลำดับ) — property ตัวเดียวขยายเป็นหลายเคส: round-trip, idempotence, invariance และ stateful model ที่รันคำสั่งเป็นชุด เก็บ seed ที่ล้มไว้และ shrink ลงให้เล็กที่สุดที่ยังล้ม
- หลักฐานที่สกิลบังคับ: รันอินพุตเดียวกันก่อนและหลัง · เทสต์เขียนที่จุดที่ผู้เรียกใช้จริง และต้องแดงเมื่อ revert ฟิกซ์แล้วกลับมาเขียว · ตั้งชื่อการเปลี่ยนแปลงในโปรดักชันที่เทสต์นั้นกัน · รายงานบรรทัดละเคสว่า «พังอะไร ที่ไหน แสดงอย่างไร» หรือ «ไม่ได้รัน เพราะอะไร»
- `references/case-heuristics.md` (56 บรรทัด) เก็บตารางฮิวริสติกกับคำถามของแต่ละตัว (boundaries, goldilocks, starvation, interruptions, configuration, sequence, count, follow the data, multi-user) พร้อม data-type attacks, หมวด state/ผู้ใช้/failure และ property shapes
- เคสที่ข้ามขอบเขตความเชื่อถือ ช้า เกี่ยวกับข้อมูลไทย ไมเกรชัน หรือต้องดูเฟรมที่เรนเดอร์ สกิลโยงไป `aetox-security-audit`, `aetox-performance`, `aetox-th-locale`, `aetox-database`, `aetox-render-check` แทนที่จะทำเอง
- เนื้อหาดัดแปลงวิธีจาก SprocketLab/slop-code-bench, obra/superpowers, j4flmao/agent-skills, rohunj/claude-build-workflow, i2nes/qa-agent-skills และ Test Heuristics Cheat Sheet (MIT/วิธีล้วน) — เขียนใหม่ทั้งฉบับและระบุที่มาใน frontmatter ของสกิล
- ลงรายการใน `aetox/SKILL.md` หนึ่งแถว เพราะ `TestTheAetoxSkillNamesEveryBundledSkill` บังคับให้ทุกสกิลที่ฝังไปกับไบนารีต้องถูกเอ่ยชื่อในดัชนี

## `placement.md`: ปุ่ม เมนู และกลุ่ม อยู่ตรงไหน

- **เดิม** `aetox-frontend-design` สอนเรื่องสี ตัวอักษร ฟอร์ม โฟกัส และคอนทราสต์ แต่ไม่มีไฟล์ที่ตอบคำถามว่า «ปุ่มหลักควรอยู่มุมไหน เมนูควรมีกี่รายการ กลุ่มควรคั่นด้วยอะไร» คำตอบจึงขึ้นกับรสนิยมของแต่ละรอบ
- **ตอนนี้** `internal/skill/skills/aetox-frontend-design/references/placement.md` (110 บรรทัด) ตอบทีละเรื่อง: หนึ่งปุ่มหลักต่อพื้นที่ที่จบงานหนึ่ง · ตำแหน่งของมันในฟอร์ม ไดอะล็อก และจอมือถือ · เมนูคือทางไป ไม่ใช่คำสั่ง (เพดาน 5–7 รายการหลัก ลึกไม่เกินสองชั้น เรียงตามการใช้งานและค่าของการพลาด ไม่ใช่ตัวอักษร) · ป้ายเป็นกริยากับกรรมและสัญญาผลลัพธ์ · ช่องว่างคือลำดับชั้นก่อนเส้นคั่น · และชุดเช็กที่รันได้จริง (สามงานหลักถึงในสองคลิกนับจากจอแรกหลังเปิดแอป, Tab ถึงปุ่มหลัก, ขาวดำแล้วปุ่มหลักยังเด่นสุด, จอตอบสามคำถาม)
- ระบบของผลิตภัณฑ์มาก่อนทุกบรรทัด สิ่งที่ไฟล์นี้ให้คือค่าตั้งต้นพร้อมเหตุของมัน และปิดท้ายด้วย «ไฟล์นี้ไม่ตัดสินอะไร» ที่โยงเรื่องหน้าตา สถานะของคอนโทรล ฟอร์ม ไปยังไฟล์ที่ดูแลเรื่องนั้นอยู่แล้ว
- `references/review.md` เพิ่มประโยคเดียว: ถ้าคำถามคือ «วางที่ไหน» กฎอยู่ใน `placement.md`
- รอบรีวิวที่ตามมาแก้สี่ข้อจากไฟล์จริง: «จอ» ถูกนิยามเป็นพื้นที่ทำงานที่จบงานหนึ่ง (workspace/แดชบอร์ดได้หนึ่งปุ่มต่อโซน จอเองไม่มี — เดิมเหมารวมจนขัดกับหน้าจอที่มีหลายโซน) · ไดอะล็อกยืนยันการทำลายได้กฎของตัวเอง (ฝั่งที่ออกจากการทำลายได้เป็นปุ่ม primary ฝั่งที่ทำลายใช้สไตล์เตือน — เดิมไม่มีอะไรอธิบายทั้งที่หน้าจอทำถูกอยู่แล้ว) · เช็ก 375px กับนิ้วโป้งแยกเป็น «ทุกพื้นผิว» กับ «เมื่อผลิตภัณฑ์รันบนมือถือ» · «สามงานในสองคลิก» นิยามจุดเริ่มและการนับ (เปิดเมนู 1 ครั้ง = 1, ไดอะล็อกที่เป็นขั้น = 1, พิมพ์และเลื่อนไม่นับ) และต้องเขียนชื่อสามงานไว้ · ป้ายของจอที่บันทึกเองต้องบอกที่ตัวหน้า ไม่ใช่ฝากไว้ที่ปุ่ม
- ข้อเสนอให้แยกกฎออกเป็นไฟล์ `rules-*` กับ audit rubric ไม่ถูกรับ: ไฟล์นี้มีหัวข้อ «The checks» แยกอยู่แล้ว และสองไฟล์ที่ต้องเปิดคู่กันจะเพี้ยนจากกันได้
- ที่มา: GOV.UK Design System กับ Service Manual (Open Government Licence v3.0), NHS digital service manual, Apple HIG สำหรับจำนวนแท็บ และสกิล information architecture สองตัวสำหรับเพดานเมนูกับความลึก — ไม่คัดลอกข้อความ
