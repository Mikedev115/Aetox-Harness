# 🪟 Aetox v1.10.25

วันที่ 29 ตุลาคม 2026

**ภาพที่เครื่องมือถ่ายและคลิปที่มันอ่านมา อยู่กับบทสนทนาต่อไปในกรอบเดียวกับภาพที่สร้างขึ้น · คำตอบยาวที่อ่านครั้งเดียวแล้วส่งต่อออกมาเป็นหน้า HTML หน้าเดียวที่พิมพ์และเก็บได้ ส่วนแผนกับโน้ตที่ยังแก้ต่อยังเป็น `.md` · งานเบื้องหลังที่ถามโมเดลครั้งเดียวได้เพดานของรุ่นเองและถามซ้ำหนึ่งครั้ง ปุ่มสรุปความจำจึงไม่ขึ้น `unexpected end of JSON input` อีก · เซิร์ฟเวอร์ภาษาที่ค้างหรือกินแรมถูกเก็บเอง และคนในห้อง 3D กระพริบตา พักมือจากคีย์บอร์ด และเดินครบสี่เฟส**

## แชท: ภาพที่เครื่องมือถ่าย และคลิปที่มันอ่านมา

- **เดิมภาพที่แคปได้ไปถึงโมเดลเท่านั้น** ผลลัพธ์ของเครื่องมือไม่มีที่ให้ภาพกลับไปหน้าต่าง บทสนทนาจึงเก็บประโยคที่พูดถึงภาพแต่ไม่มีภาพ แถวขึ้นว่า «จับภาพหน้าจอ» แล้ววาดอะไรไม่ได้ และเซสชันที่เปิดใหม่พรุ่งนี้เห็นเทิร์นที่อ้างถึงภาพซึ่งไม่มีใครดูได้ (รายงานจากเทสเตอร์บนแอปที่ปล่อยจริง 28 ต.ค. 2026)
- **ทุกภาพที่การเรียกสร้างหรือถ่ายขึ้นเป็นกรอบเดียวกัน** `ToolPart.Shots` รับภาพจากแคปหน้าจอเบราว์เซอร์ แคปหน้าต่าง และภาพจาก `image_make` เดินผ่าน `fileURL` ตัวเดียวกับภาพที่ผู้ใช้แนบ กดแล้วเปิดในแผงภาพเดิม
- **ภาพถูกเขียนลง part ไม่ต้อง migration** เป็นฟิลด์ใหม่ในคอลัมน์เดิม แถวเก่าอ่านแล้วไม่มีค่าเหมือนที่เคยเป็น และภาพยังอยู่หลังรีสตาร์ต ไม่ใช่แค่ตอนเทิร์นกำลังไหล
- **แคปที่ภาพไม่เปลี่ยนอ้างถึงภาพเดิม** ยังไม่เขียนไฟล์ซ้ำและไม่ส่งไบต์ซ้ำ แต่แถวได้พาธของแคปก่อนหน้าจึงมีภาพให้ดู ไม่ใช่ช่องว่าง
- **ลิงก์ที่เป็นวิดีโอหรือเสียงกลายเป็นบัตร** `web_fetch` อ่าน `og:type` `og:title` `og:image` และความยาวในรอบเดียวกับที่อ่านข้อความ รวม `lengthSeconds` กับ `duration` ในบล็อก `ld+json` ของ schema.org จึงไม่มีคำขอเพิ่ม บัตรมีชื่อ บรรทัด `ต้นทาง · ความยาว` โปสเตอร์ 16:9 และปุ่มเล่น กดแล้วเปิดในแท็บเบราว์เซอร์ของแอป เดิมได้ประโยคกับ URL ที่ต้องเอาไปเปิดเอง
- **บัตรที่ไม่มี URL ถูกทิ้ง** เพราะการ์ดที่กดไม่ได้คือโปสเตอร์ที่โกหก แต่ความยาวหรือโปสเตอร์ที่หน้าไม่ได้บอกไม่มีปัญหา บัตรยังเป็นทางกลับไปหาหน้าได้
- **ช่วงที่มีบัตรหรือภาพไม่ถูกพับเป็นบรรทัดเดียว** เดิมบัตรโผล่ตอนคำตอบไหล แล้วหายตอนเทิร์นจบ («มันค้นลิงก์มาแล้วก็พับไป»)
- **เทิร์นที่กำลังทำงานไม่ถูกทับด้วยหน้าแรก** เดิมเลือกจอจาก `messages.length === 0` เทิร์นที่คำถามไม่ได้อยู่ในลิสต์ของหน้าต่าง (แชทที่ถูกปลุกจากอีกแชท ข้อความจากบอท หรือช่วงระหว่างกดส่งกับฟองข้อความขึ้น) จึงวาดหน้าแรกทับแถว คำตอบ ภาพและบัตรทั้งหมดที่มันเพิ่งทำ ตอนนี้นับ `awaitingReply` เป็นเทิร์นที่ยังไม่จบด้วย
- **ลากภาพจาก Explorer ลงช่องพิมพ์มีปฏิกิริยา** เดิมลากสลิปมาวางแล้วไม่มีอะไรสว่าง ความเงียบนั้นอ่านได้ว่าแอปไม่รับภาพจากข้างนอก ตอนนี้กล่องติดและขึ้นการ์ดชื่อไฟล์ที่จะแนบ (หลายไฟล์บอกจำนวนที่เหลือ) ตัว drop ยังเป็นของ Wails ที่อ่านพาธตามพิกัด จึงไม่ `preventDefault` ที่นี่

## คำตอบ: หน้าเดียวที่พิมพ์ได้ และปิดท้ายด้วยผล

- **เดิมทุกคำตอบยาวเป็นไฟล์ `.md`** เหตุผลเดิม (เรนเดอร์ในแชท เปิดได้ทุกโปรแกรม แก้หนึ่งครั้ง) ใช้กับไฟล์ที่ยังต้องทำงานต่อ ไม่ใช่สิ่งที่อ่านครั้งเดียวแล้วส่งต่อ: สรุปมาถึงเป็นคอลัมน์แบน ๆ ในแผง artifact ที่พิมพ์ไม่ได้ ขณะที่เนื้อหาเดียวกันเป็นหน้าเปิดเต็มความกว้าง พิมพ์ได้ และออกเป็น PDF ผ่านเครื่องมือที่ deck export มีอยู่แล้ว
- **สรุป รายงาน ผลค้นหา และการเทียบ เป็น `.html` หน้าเดียว** แผน สเปก ชุดโน้ตที่ยังต้องแก้ต่อ หรือไฟล์ที่ลูกมือต้องอ่าน ยังเป็น `.md` เพราะต้องเติมได้ทั้งสองฝ่าย
- **หน้านั้นไม่ได้เขียนลอย ๆ** สกิล `aetox-report` บอกว่ารูปแบบไหนพาข้อมูลแบบไหน (ตัวเลขเดี่ยว กราฟ แผนภาพ ตารางเทียบ รูป) ลำดับที่อ่านรู้เรื่อง และอะไรทำให้ผู้อ่านเชื่อหน้า รูปทรงของรายงานยังเป็นของโมเดลตัดสินทีละเรื่อง ไม่ใช่เทมเพลตตายตัว
- **ชื่อสกิลถูกเอ่ยเฉพาะเดสก์ที่เปิด `skill_view` ได้** เดสก์ที่ไม่มีประตูนั้นยังได้ค่าเริ่มต้นเป็นหน้าเว็บ แต่ไม่ถูกชี้ไปยังเอกสารที่เปิดไม่ได้
- **คำตอบปิดเทิร์นเป็นบทสรุปของผล ไม่ใช่รายงานการทำงาน** ทั้งโหมดผู้ช่วยและโต๊ะโค้ด: บรรทัดละหนึ่งจุด ไม่เล่าขั้นตอนซ้ำ และไม่พูดซ้ำสิ่งที่ผู้ใช้เห็นในผลของเครื่องมือแล้ว ประโยค «บอกว่าอะไรตรวจแล้ว อะไรยังไม่ได้ตรวจ อะไรล้ม» ยังอยู่ครบ เพราะประโยคใหม่คุมวิธีพูด ไม่ใช่สิ่งที่ต้องรายงาน
- **เงื่อนไขการวาดขยายถึงตัวอย่างที่ต้องถือหลายส่วนพร้อมกัน** เดิมครอบเฉพาะคำอธิบายความสัมพันธ์ ลำดับ การแบ่ง หรือก่อน–หลัง ตัวอย่างที่มีห้าส่วนจึงออกมาเป็นย่อหน้า พร้อมกันนั้นมีประโยคเตือนว่าภาพที่คำพูดบอกอยู่แล้วในบรรทัดเดียวคือของประดับที่ผู้ใช้ต้องรอวาดทุกเส้น

## งานเบื้องหลัง ไดอารี่ และบอท

- **เดิมเพดานคำตอบของงานเบื้องหลังคิดจากขนาดของข้อความที่อยากได้** ปุ่มสรุปความจำขอ 2,000 token ขณะที่ต้องย่อข้อความไทย 2,155 ตัวอักษร (จาก 2,883 ใน `MEMORY.md` ของเจ้าของ) ให้ต่ำกว่า 5,397 ไบต์ คำตอบจึงถูกตัดกลาง JSON แล้วจอขึ้น `unexpected end of JSON input` ของ Go แทนคำอธิบาย
- **ตัวเขียนข้อความคอมมิตขอ 700 token** ซึ่งเป็นขนาดของข้อความ ไม่ใช่ขนาดของงาน โมเดลแบบ thinking เอาโทเคนนั้นไปคิดจนหมดก่อนคำแรก คำตอบกลับมาเปล่า การ์ดขึ้น `model wrote nothing` และปุ่มลองใหม่ก็ยิงด้วยเพดานเดิม ล้มแบบเดิมทุกครั้ง
- **เพดานอยู่ที่เดียวและเป็นของรุ่น** `oneShotOutputCeiling` ใน `internal/engine/oneshot.go` อ่านเพดานเอาต์พุตของรุ่นจาก catalog และใช้ 8192 เมื่อไม่รู้จักรุ่น งานที่ถามครั้งเดียวทุกงานใช้ตัวเดียวกัน ทั้ง session review, อ่านหน้าเว็บ, prepared reply, สรุปการประชุม, ดึงไอเดีย, บันทึกไดอารี่, ตอบจาก knowledge, อธิบายข้อความที่เลือก และร่างสกิล ส่วนการจัดกลุ่มคอมมิตคงเพดานของมันเองเพราะต้องจุทุก path
- **คำตอบที่ถูกตัดได้ถามซ้ำหนึ่งครั้ง สั้นลง** ผ่าน `askToolJSON` ที่อ่าน tool call ตามชื่อ ไม่ใช่ตามลำดับ ผู้ให้บริการที่ปฏิเสธไม่ถูกถามซ้ำ และโทเคนของทั้งสองครั้งถูกนับ เพราะครั้งที่ถูกตัดก็คือโทเคนที่ผู้ใช้จ่ายไปแล้ว
- **ความล้มเหลวเป็นรหัสและประโยคที่ทำอะไรต่อได้** `commit-message-empty` ให้หน้าจอแปลเป็นภาษาผู้ใช้เอง และข้อความที่ถูกตัดกลางประโยคไม่ถูกส่งไปเป็นคอมมิต เพราะรายการไฟล์ที่อยู่ใน commit เป็นคำตอบที่ดีกว่าประโยคที่หยุดกลางทาง
- **ไดอารี่รอแค่ 5 นาที** (เดิม 10) เพราะวันทำงานแทบไม่เคยเว้นช่วงยาวกว่านั้น และบันทึกเคยไปถึงเที่ยงคืนโดยที่ของเมื่อวานยังขาด ตัวเขียนยังใช้เพดาน 2,000 และบังคับ tool call ครั้งเดียว จึงเงียบทั้งวันเมื่อผู้ให้บริการไม่ยอมเรียกเครื่องมือ ตอนนี้ใช้เพดานของรุ่น ถามซ้ำแบบไม่บังคับ และ error บอกสิ่งที่ผู้ให้บริการตอบมาจริง แทน `the model wrote no entry` ที่ไม่บอกอะไรเลย
- **วันที่ไม่มีบันทึกบอกได้ว่ายังไม่ถึงคิวหรือเขียนไม่ผ่าน** `BrainDays` ส่ง `retrying` (วัน → เวลาที่จะลองอีก) ให้ปฏิทิน และหน้าโน้ตขึ้นวันนี้ก่อนเสมอ
- **บอทเงียบได้ทีละตัวด้วย `/notify off`** เป็นคำสั่งควบคุมจึงใช้ได้แม้มีงานกำลังทำ สถานะเก็บที่ platform id เดียวกับที่ตัวส่งข้อความใช้ บอทตัวหนึ่งเงียบได้โดยอีกตัวยังพูด ประกาศที่ปิดคือ งานเสร็จ งานตั้งเวลา และเตือนความจำ ส่วนคำถามที่งานหยุดรอคำตอบยังส่งมาถึงเสมอ เพราะการปิดคือการหยุดงานที่มันถามอยู่ และเตือนความจำที่ไม่มีใครให้บอกยังขึ้นในแชทของแอป
- **ประกาศเป็นสรุป ไม่ใช่คำตอบทั้งก้อน** เดิมส่งยาวได้ถึง 3,000 ตัวอักษร ตอนนี้เอา 6 บรรทัดแรก ไม่เกิน 600 ตัวอักษร และถอดมาร์กอัปออก (`**` `#` backtick เครื่องหมายคำพูด bullet และที่อยู่ลิงก์) เพราะ Telegram แสดงมาร์กอัปตามที่โมเดลพิมพ์ คำยังเป็นของโมเดล ไม่มีอะไรถูกเขียนใหม่
- **สวิตช์บนหน้าช่องทางเขียนผ่านทางเดียวกับคำสั่ง** `SetChannelNotices` บันทึกลง `BotNoticesOff` แล้วส่ง `channel_notices_off` ไปกับสถานะชุดเดิม จอกับคำสั่งจึงไม่เถียงกัน และค่าถูกอ่านตอนจะแจ้ง ไม่ใช่จำไว้ตั้งแต่บูต สำเนาในหน่วยความจำจะพูดต่อไปหลังเจ้าของสั่งให้หยุด

## ตัวแก้โค้ด: เซิร์ฟเวอร์ภาษาที่ค้าง MCP ที่ปิดไม่จบ และลูกมือ general

- **เซิร์ฟเวอร์ภาษาถูกเฝ้าแล้ว** วัดในเช็กเอาต์นี้เมื่อ 28 ต.ค. 2026: `svelte-language-server` เปิดมาตั้งแต่ 17:26 เผาไป 2,700 วินาทีซีพียูถึง 18:15 (1.5–2.1 ของ 16 คอร์ ตลอดเวลา) และถือแรม 1.25 GB ขณะที่ตัวใหม่บนโปรเจกต์เดียวกันนิ่ง 0.06 คอร์ และตัวที่ค้างอ่านดิสก์ 0 ops/วินาที คือวนอยู่ในหน่วยความจำตัวเอง ไม่มีอะไรในแอปสังเกต เพราะเอดิเตอร์ว่างกับเซิร์ฟเวอร์ที่ค้างหน้าตาเหมือนกันจากข้างนอก
- **ตัวเฝ้าตัดสินสองเรื่อง** ไม่มีคำขอ 1 นาทีและใช้เกินครึ่งคอร์ติด 4 รอบ (2 นาที) → ปิด ครั้งหน้าที่ต้องใช้เปิดใหม่ · ไม่มีแท็บเปิดและไม่มีคำถาม 10 นาที → คืนแรม ไม่แตะตอนกำลังตอบ ตอนยังไม่เคยตอบ (กำลัง index) หรือระบบที่วัดซีพียูไม่ได้ ทดสอบกับของจริง: โปรเซสที่หมุนเต็มคอร์ผ่าน `cmd.exe` ถูกจับและปิดใน 124 วินาที

## ห้อง 3D: คนที่ทำงานจริง และของที่ขยับเอง

- **rig อบท่าละ 4 เฟส แต่ห้องขอแค่ 2** คือ `p0`/`p2` ทุก 1.8 วินาที และไม่เคยขอ `blink: shut` คนในห้องจึงไม่เคยกระพริบตา («มีหลาย ๆ ท่าทางหน่อย ให้เหมือนคนจริง ๆ») ตอนนี้ `poseFrame()` ตัวเดียวให้ทั้งแผนและโมเดล: จังหวะตามท่า (พิมพ์ 0.45 วินาที/เฟส นั่ง 1.8) และกระพริบตาทุก 3–6 วินาที คนละจังหวะจาก seed
- **คนที่กำลังคุยใช้ท่า `answering` หันหน้าตามคู่สนทนา** ไม่ใช่เฟรมเดิน `p0` ค้างที่อ่านเป็นการยืนนิ่งกลางอากาศ
- **งานยาวไม่ใช่ท่าเดียว** ทุก 2–4 นาที มือออกจากคีย์บอร์ด จิบน้ำ หาว หรือมองรอบ 1.6–2.4 วินาที แล้วกลับมาทำงาน (ไม่ลุกจากเก้าอี้) และคนที่นั่งถูกเลื่อนเข้าหาโต๊ะ 0.16 ช่อง อ่านเป็นนั่งหลังจอ ไม่ใช่ยืนข้างโต๊ะ
- **«ทำไมท่าเดินพัง»** `family()` คืนเฉพาะเฟส 0 กับ 2 และเฉพาะ `blink: open` พอห้องเริ่มขอเฟส 1/3 และเฟรมกระพริบ คีย์พวกนั้นไม่เคยถูกส่งเข้าคิวอบ ตัววาดจึงตกไปใช้เฟรมยืน ขาไม่ขยับแต่ตัวสไลด์ ตอนนี้คืนทุกเฟสและเฟรมกระพริบของท่าที่ขอ (เฟรมที่ขอมาก่อน) จุดยึดของเฟรมเดินใช้กับ `state moving` เท่านั้น เพราะท่านั่งที่วาดด้วยจุดยึดเดินจะลอย เฟรมเดินถูกไล่ท้ายสุด และ `HOT` ขึ้นจาก 240 เป็น 288
- **ของที่ขยับเองในห้องถูกวาดในโมเดล 3D ด้วย** `ambient.ts` ส่ง `kind`/`hue` ของแต่ละ prop มานานแล้ว (กล่องงานเสร็จที่ลอยไป Delivery และหุ่นดูดฝุ่นกลางคืน) แต่ `view.ts` ไม่เคยอ่าน `scene.props` ห้องจึงนิ่งตอนที่ไม่มีใครลุกจากโต๊ะ ตอนนี้กล่องเป็นลูกบาศก์สีทีม หุ่นดูดฝุ่นมีตากะพริบ และ `frame()` นับ prop ที่ขยับเป็นการเคลื่อนไหว ไม่ลดเฟรมลงตอนห้องนิ่ง
- **หน้าพนักงานเฉพาะทางเป็นสองคอลัมน์** เดิมเป็นการ์ดสามคอลัมน์กว้าง 240px คำอธิบายถูกตัดกลางคำที่บรรทัดสาม ปุ่ม «คุยกับ …» ซ้ำสิบสองครั้งใต้คนสิบสองคน และแถวชิปอีกสิบสองปุ่มบีบป้าย «งานที่รับมา» จนตั้งเป็นคอลัมน์ตัวอักษร ตอนนี้คนอยู่ซ้าย (หน้า ชื่อ จำนวนงาน) งานของคนที่เลือกอยู่ขวา และการเลือกคนคือการกรองฟีด เหลือตัวควบคุมเดียวจากที่เคยมีสอง แถว «ทั้งหมด» บนสุดยังพาดูงานของทั้งทีม
