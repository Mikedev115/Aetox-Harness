# 🪟 Aetox v1.10.24

วันที่ 28 ตุลาคม 2026

**เซิร์ฟเวอร์ MCP ที่หลุดเชื่อมต่อกลับมาเองได้ตามเวลาที่ห่างขึ้น พร้อมนับถอยหลังบนแถวที่กำลังรอ และสีแดงเก็บไว้ให้เฉพาะที่ต้องแก้เอง · ตัวแก้โค้ดสตาร์ตเซิร์ฟเวอร์ภาษาในโปรเจกต์ของไฟล์แทนรากเวิร์กสเปซ — 105 วินาทีซีพียูเหลือ 0.8 และเส้นเตือนในแท็บกลับมา · และไดอารี่ที่วันหนึ่งเขียนไม่ได้ไม่พาทั้งสัปดาห์หายไปด้วย**

## MCP: เซิร์ฟเวอร์ที่หลุดเชื่อมต่อกลับมาเอง

- **เดิมคำว่า failed เป็นคำตัดสินถาวร** `mcp.Client` จำความล้มเหลวไว้ (ที่ `ensure`) สิ่งเดียวที่ลองใหม่ได้คือคนกด `ทดสอบ` บันทึกเซิร์ฟเวอร์ใหม่ หรือจบการเข้าสู่ระบบ — แต่เคสที่ทำให้เรื่องนี้ต้องแก้ล้วนเป็นเหตุที่หายเอง: แล็ปท็อปที่เปิดก่อนไวไฟขึ้น ท่าที่ขอโทเคน timeout ตอนตีสี่ และเซิร์ฟเวอร์โลคอลที่เพิ่งสตาร์ตตามมาทีหลัง
- **แยกความล้มเหลวเป็นสี่ชนิดตามสิ่งที่ต้องทำต่อ** `FailureKind` มี `network` (สาย: ไม่มีเส้นทาง, DNS, timeout, หลุด) · `local` (เซิร์ฟเวอร์บนเครื่องเดียวกันที่ยังไม่ขึ้น) · `auth` (สิทธิ์ถูกปฏิเสธ) · `config` (ไม่มีที่อยู่ให้ลองเลย) การจำแนกอ่านจากข้อความ error เพราะ SDK ไม่ส่ง typed error มาให้ และชนิดที่อ่านไม่ออกเป็น `unknown` ซึ่ง**ถูกลองใหม่** เพราะความล้มเหลวที่ไม่รู้จักมักเป็นเน็ตที่ไม่มีใครเห็น มากกว่าค่าตั้งที่ไม่มีวันทำงาน ส่วน backoff เป็นตัวจำกัดราคาของการเดานั้น
- **401/403 ถูกจับด้วยขอบเขตคำ** พอร์ต `4401` จึงไม่ถูกอ่านเป็นสถานะ 401 ซึ่งเคยทำให้เซิร์ฟเวอร์ที่แค่ยังไม่ขึ้นถูกจัดเป็นความผิดเรื่องโทเคน
- **`Retry()` ล้างคำตัดสินเดิมแล้วต่อใหม่** ต่างจาก `ensure()` ที่ตรึงความล้มเหลวไว้ตลอดเทิร์น — ซึ่งถูกต้องสำหรับผู้เรียกที่อยู่ในการตอบหนึ่งครั้ง แต่ผิดสำหรับตัวที่เฝ้าอยู่ข้างนอก
- **ตัวเฝ้าการเชื่อมต่อไล่ตรวจทุก 5 วินาที** ต่อเซิร์ฟเวอร์ตามเวลาที่ห่างขึ้น 30 วินาที → 1 → 2 → 5 นาที จำกัดเวลาต่อครั้งไว้ 90 วินาที และไม่ยิงซ้อนขณะกำลังลองอยู่ รอบที่สำเร็จล้างประวัติของเซิร์ฟเวอร์นั้น การหลุดครั้งหน้าจึงเริ่มจาก 30 วินาที ไม่ใช่จากที่การล่มครั้งก่อนไปถึง
- **แตะเฉพาะความล้มเหลวที่หายเองได้** `auth` กับ `config` ปล่อยให้คนแก้ เพราะการลองซ้ำกับโทเคนที่เซิร์ฟเวอร์ปฏิเสธแล้วคือการทะเลาะเป็นรอบ ๆ ไม่ใช่การซ่อม
- **สมุดบันทึกการลองอยู่ที่ Engine ไม่ใช่ Manager** Manager ถูกสร้างใหม่ทุกครั้งที่ re-bootstrap แต่ความอดทนไม่ควรถูกรีเซ็ตตาม
- **เครื่องมือของเซิร์ฟเวอร์ที่กลับมาได้ ถูกใส่เข้าแชทที่เปิดอยู่ทันที** `registerMCP` ทำงานครั้งเดียวตอนบูต จึงไม่ครอบเคสที่เซิร์ฟเวอร์กลับมาทีหลัง — ตอนนี้ถูกเรียกซ้ำให้เฉพาะเซิร์ฟเวอร์นั้น
- **หน้าจอได้ `kind` `retryAt` `retrying` มาด้วย** แทนที่จะต้องเดาจากข้อความ error ดิบ และได้ event `mcp:status` ทุกครั้งที่รอบหนึ่งจบ

## MCP: แถวที่กำลังรอเป็นสีรอ ไม่ใช่สีแดง

- **เดิม "พัง" กับ "กำลังถูกซ่อม" หน้าตาเหมือนกัน** ทั้งคู่เป็นแถวแดงพร้อมข้อความจากชั้น transport ที่คนอ่านใช้ต่อไม่ได้
- **แถวที่ตัวเฝ้ากำลังดูแล เปลี่ยนเป็นโทนรอ** `รอเน็ต` · `รอโปรแกรม` (เซิร์ฟเวอร์บนเครื่องเดียวกัน) · `กำลังต่อใหม่` พร้อมบรรทัด `ลองอีกใน n วิ` ที่นับจากเวลาจริงที่ตัวเฝ้าจะลองอีกครั้ง
- **ปุ่ม `ลองเลย` ข้ามการรอ** สำหรับคนที่ไม่ต้องการรอ 30 วินาที
- **สีแดงเหลือให้เฉพาะแถวที่ต้องมีคนลงมือ** `auth` กับ `config` และแถวนั้นไม่มีนับถอยหลัง เพราะการนับถอยหลังบนสิ่งที่ไม่มีใครกำลังทำ คือการบอกผิดว่าเดี๋ยวจะหายเอง
- **เหตุที่ต่อไม่ได้เขียนเป็นประโยคที่ใช้ได้** `ยังต่อ example.com ไม่ได้ — เน็ตยังไม่ถึง` · `บัญชี X ต้องเข้าสู่ระบบใหม่` · `ที่อยู่ของ X ยังไม่ครบ — ต้องแก้ที่ตั้งก่อน` · และเซิร์ฟเวอร์โลคอลบอกพอร์ตที่ต้องเปิด ส่วน error chain ดิบยังอยู่ครบในชีตหลัง `รายละเอียดทางเทคนิค`
- **แถบสรุปบอกจำนวนที่กำลังรอ** `รอเชื่อมต่อ 2: fs, playwright` ต่อจากบรรทัดอื่นที่แถบนี้มีอยู่แล้ว
- **ตัวนับเวลาเดินเฉพาะตอนมีแถวรอ** หน้าที่ไม่มีอะไรให้นับไม่ถือ timer ไว้เลย
- **รายการรีเฟรชเพราะได้ยิน ไม่ใช่เพราะถามซ้ำ** หน้าจอฟัง `mcp:status` แล้วโหลดใหม่เฉพาะตอนที่คำตอบเปลี่ยน

## ตัวแก้โค้ด: เซิร์ฟเวอร์ภาษาสตาร์ตในโปรเจกต์ของไฟล์

- **เดิมทุกเซิร์ฟเวอร์สตาร์ตที่รากเวิร์กสเปซ** ซึ่งเป็นโฟลเดอร์ที่ผิดสองต่อ: รีโปนี้มีทั้งแอป Svelte, โค้ด Go, แอปของโทรศัพท์ และ `third_party` เซิร์ฟเวอร์จึงสร้างโปรแกรมทับทั้งหมด และโปรไฟล์ของบิลด์ dev อยู่ใต้เช็กเอาต์เอง (`desktop/.aetox-data` — เขียนไป 2,985 ไฟล์ใน 12 นาที) ตัวเฝ้าไฟล์ที่ตั้งรากไว้ที่นั่นจึงไม่เคยเงียบ
- **วัดในเช็กเอาต์นี้ (441,493 ไฟล์) ด้วยเซิร์ฟเวอร์ตัวเดียวกัน ต่างกันแค่โฟลเดอร์** รากเวิร์กสเปซ: 105 วินาทีซีพียูใน 100 วินาที ใช้ 2.2 GB และ**ไม่ได้ diagnostics ของไฟล์ที่ถามเลย** · `desktop/frontend`: 0.8 วินาทีซีพียูในสองนาทีถัดมา ใช้ 99 MB และ diagnostics กลับมาใน 11.8 วินาที
- **รากของเซิร์ฟเวอร์คือโปรเจกต์ที่ใกล้ไฟล์ที่สุด** หาได้จาก `tsconfig.json` `jsconfig.json` `svelte.config.js` `package.json` `go.mod` `pyproject.toml` `Cargo.toml` ไฟล์ที่ไม่มีโปรเจกต์อยู่เหนือขึ้นไปใช้รากเวิร์กสเปซเหมือนเดิม
- **ไฟล์นอกรากเวิร์กสเปซยังคงใช้รากเวิร์กสเปซ** เพื่อไม่ให้เซิร์ฟเวอร์ไปอ่านพาธที่หน้าต่างไม่มีสิทธิ์
- **เซิร์ฟเวอร์ที่กำลังรันถูกคีย์ด้วยคำสั่งบวกโฟลเดอร์ราก** สองโปรเจกต์ในเวิร์กสเปซเดียวจึงได้คนละเซิร์ฟเวอร์ ไม่ปนโปรแกรมกัน
- **เส้นเตือนในแท็บกลับมา เมื่อเซิร์ฟเวอร์สะกด URI ต่างจากที่ส่งไป** เซิร์ฟเวอร์บน Windows ตอบเรื่อง `file:///d%3A/...` ให้ไฟล์ที่หน้าต่างเปิดเป็น `file:///D:/...` การค้นแบบตรงตัวจึงไม่เจออะไร แท็บไม่มีเส้นเตือนแม้แต่เส้นเดียว ขณะที่ Problems list รายงานไฟล์เดียวกันไว้สองคำเตือน — ในเซสชันเดียวกันนั้น hover ทำงาน เพราะเอกสารคีย์ด้วยการสะกดของเรา แต่ diagnostics คีย์ด้วยของเซิร์ฟเวอร์
- **ตอนนี้ค้นด้วยการเทียบว่าเป็นเอกสารเดียวกัน** และตอนปิดแท็บ ล้าง diagnostics ของเอกสารนั้นทุกการสะกด ไม่ให้ค้างใน Problems list ของแท็บที่ไม่มีใครเปิดอยู่

## ไดอารี่: วันที่เขียนไม่ได้หยุดแค่วันนั้น

- **27 ตุลาคม โมเดลตอบกลับมาเปล่าทุกครั้งที่พาสเขียนบันทึก** ลูปเดิม `return` ทันทีเมื่อวันใดวันหนึ่งล้ม วันถัดไปซึ่งมีข้อความใหม่กว่าหนึ่งร้อยข้อความจึงไม่เคยถูกแตะเลย และวันเดิมก็ถูกลองซ้ำทุกช่วง idle โดยไม่มีเพดาน
- **วันหนึ่งล้มคือปัญหาของวันนั้น** เก็บการล้มไว้ ข้ามไปวันถัดไป แล้วคืน error รวมตอนจบ — วันที่เหลือยังได้โน้ตของตัวเอง
- **การยกเลิกทั้งพาสยังหยุดทันที** และไม่ถูกนับเป็นความผิดของวันนั้น เพราะสาเหตุคือมีเทิร์นเริ่มขึ้นหรืองบหมด ไม่ใช่โมเดลเขียนไม่ได้
- **วันที่ล้มพักก่อนลองใหม่** migration 73 `journal_retry` จำจำนวนครั้งที่ล้มติดกันและเวลาที่จะลองอีก: 30 นาทีหลังครั้งแรก ทบทีละเท่าถึงเพดาน 4 ชั่วโมง และล้างเมื่อเขียนสำเร็จ — วันที่โมเดลไม่ยอมเขียนจึงเสียไม่กี่ครั้งต่อวัน ไม่ใช่ทุกช่วง idle
- **ปุ่ม `จดตอนนี้` ข้ามระยะพักได้** เพราะการกดคือคนที่กำลังขอให้เขียนเดี๋ยวนี้
